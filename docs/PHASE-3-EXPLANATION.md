# Phase 3 — Word Generator Module
## Explanation, Rationale & Context

**What is Phase 3?**  
Phase 3 builds the content pipeline that feeds the crossword engine with
high-quality, themed word/clue pairs. Without it, each puzzle draws from a
~75-word hand-curated list, which limits how many words the layout engine can
intersect. With it, each theme gets 150+ words generated by Claude — including
the short 3–5 letter bridge words that professional crosswords depend on for
density — all with publication-quality clues.

**Why is it its own phase?**  
Phase 2 solved the *structural* density problem (custom backtracking engine,
compaction). Phase 3 solves the *content* density problem. The engine can only
intersect words that exist in the list. No algorithm change fixes a list of
75 long words. Phase 3 is the "higher dimension" answer: more and better words.

**How does the pipeline flow?**
```
CSV on disk (existing ~75 words)
  ↓ loadExistingCsv()          [csv.writer / CLI]
  ↓ buildPrompt()              [prompt.builder]     → system + user message
  ↓ callClaude()               [claude.client]      → raw API response text
  ↓ parseResponse()            [response.parser]    → validated GeneratedWord[]
  ↓ deduplicate()              [deduplicator]       → merged, no dupes
  ↓ writeWordsCsv()            [csv.writer]         → expanded CSV on disk
  ↓ generate-book pipeline picks it up automatically
```

## Step 3-1 — `types.ts` + `prompt.builder`
✅ **Complete — 33/33 tests**

### What
Two files: a shared type definitions module and the prompt construction module.

`types.ts` defines `GeneratedWord`, `GeneratorOptions`, `GeneratorResult`,
`ApiError`, and eight constants (`MIN_WORD_LENGTH`, `MAX_WORD_LENGTH`,
`MAX_CLUE_LENGTH`, `MIN_SYLLABLES`, `MAX_SYLLABLES`, `MIN_YIELD_FRACTION`,
`DEFAULT_COUNT`, `DEFAULT_MAX_RETRIES`).

`prompt.builder.ts` exports `buildPrompt(opts)` → `{ system, user }` and
`getSystemPrompt()`.

### Why
**Types first** — every other module imports from `types.ts`. Defining them
before any logic prevents duplication and ensures the whole pipeline agrees on
what a `GeneratedWord` looks like.

**Prompt separation** — the system prompt (stable, never changes between
themes) and the user message (theme-specific, varies per call) are returned
as separate strings. This maps cleanly to the Claude API's `system` parameter
and `messages[0].content`. It also means the system prompt can be audited and
updated independently without touching the per-theme logic.

### How — Clue craft guidelines
The system prompt is the most important part of the whole module. It does not
ask Claude to "generate word/clue pairs." It frames Claude as a *master
crossword editor with decades of publication experience* and teaches four
specific clue-writing techniques:

- **Misdirection:** lead the solver's mind the wrong way first
- **Double meaning:** exploit words with multiple valid senses
- **Contextual framing:** set a scene rather than define
- **Economy:** fewest words that still misdirect

A `NEVER` block explicitly bans: copying the answer word, dictionary-style
definitions, "relating to" / "pertaining to" phrasing, and clues over 120
characters. Concrete examples are given for each difficulty tier.

This is what separates a puzzle book people enjoy from one they abandon.

## Step 3-2 — `response.parser`
✅ **Complete — 38/38 tests**

### What
A defensive boundary between the raw Claude API text and the rest of the
pipeline. Exports `parseResponse(raw, expectedCount?)` → `ParseResult`.

`ParseResult` contains:
- `words: GeneratedWord[]` — validated, normalised entries
- `totalFound: number` — entries in the JSON before validation
- `totalDropped: number` — entries rejected
- `dropReasons: DropReason[]` — one reason per rejected entry (for debugging)

### Why
Claude is instructed to return JSON only, but it sometimes adds markdown
fences, preamble sentences, or trailing text. Even when the JSON is clean,
individual entries may fail constraints: non-letter characters, clue too long,
invalid difficulty, out-of-range syllables. The parser handles all of this
silently — bad data is dropped, good data flows through. **It never throws.**

Why never throw? Because a partial result (15 valid words instead of 20) is
better than a crash. The retry logic lives upstream in `word.generator` — it
decides whether to call the API again based on yield. The parser's job is only
to extract the maximum value from whatever it receives.

### How
Five sequential steps:
1. **Strip fences** — ```` ```json ``` ```` patterns removed
2. **Extract array** — find the first `[` and last `]` in the text
3. **Parse JSON** — `JSON.parse`, returns empty on failure
4. **Validate each entry** — word (letters only, length), clue (length),
   difficulty (enum), syllables (integer, range)
5. **Yield warning** — logs if valid count < 60% of `expectedCount`

Key normalisation: words are uppercased; leading/trailing whitespace is
trimmed from both word and clue; `"syllables": "3"` (string) is coerced to
`3` (number) because Claude sometimes quotes numbers despite instructions.

## Step 3-3 — `deduplicator`
✅ **Complete — 17/17 tests**

### What
Merges an incoming word list (from Claude) with an existing one (from the
source CSV), removing duplicates. Exports `deduplicate(incoming, existing)`
→ `DeduplicateResult`.

`DeduplicateResult` contains:
- `merged: GeneratedWord[]` — existing words + new non-duplicate words
- `added: number` — how many incoming words were accepted
- `removed: number` — how many incoming words were dropped as duplicates

### Why
Every theme already has a hand-curated ~75-word CSV. Those words have been
reviewed; their clues may be better than what Claude generates. The
deduplicator ensures:

1. **Existing clues are never overwritten** — if HIEROGLYPH is already in the
   list with a great clue, the Claude-generated HIEROGLYPH clue is dropped
2. **Incoming words don't duplicate each other** — Claude sometimes returns
   the same word twice in one response; only the first instance survives
3. **The merged list is deterministic** — existing words always appear first
   in their original order, new words appended after

### How
The algorithm is O(n) using a `Set` for O(1) membership tests:
1. Build `existingKeys` set from `existing.map(w => w.word.toUpperCase())`
2. For each incoming word: if key is in set → drop (removed++); else → add to
   set AND to `newWords` (prevents incoming self-duplication)
3. Return `[...existing, ...newWords]`

The set is mutated as new words are added, which is what handles
incoming-vs-incoming deduplication without a second pass.

**Immutability:** neither input array is mutated. This is tested explicitly.

### Invariant
`added + removed === incoming.length` — always. Every incoming word is
accounted for in exactly one of the two counters.

## Step 3-4 — `csv.writer`
🔄 **In progress**

### What
Reads an existing CSV into `GeneratedWord[]` and writes a `GeneratedWord[]`
back to disk as a properly-formatted CSV. Two exports:

```typescript
readWordsCsv(filePath: string): GeneratedWord[]
writeWordsCsv(words: GeneratedWord[], outputPath: string): void
```

### Why
The pipeline needs to get words *out of* existing CSVs (to feed the
deduplicator's `existing` argument) and write the merged result *back to*
disk. These two operations are symmetric and belong in the same module.

**Why not use a CSV library?**  
The format is simple (`word,clue,difficulty` — three columns, one header row).
A purpose-built reader/writer is 30 lines, has no external dependency, and
handles the only real complexity: clues that contain commas must be
double-quoted per RFC 4180.

**Why must it be format-compatible with `loadWordList()`?**  
The CLI's `generate-book` command reads word lists with `loadWordList()` from
`apps/cli/src/commands/generate-book.ts`. The output of `csv.writer` goes
directly into that same pipeline. Any format mismatch silently produces
empty puzzles. Compatibility is verified in tests.

### How
**Writing:** iterates `words`, formats each as `word,"clue",difficulty`
(clue always double-quoted to handle internal commas), joins with `\n`,
prepends the header, writes with `fs.writeFileSync`. Creates the output
directory if it doesn't exist.

**Reading:** reads the file, splits on `\n`, skips the header, parses each
row. Handles quoted clues (strips surrounding `"`). Skips blank lines.
Returns only rows with all three fields populated.

```

## Step 3-5 — `claude.client`
⬜ **Pending**

### What
A thin, focused wrapper around the Anthropic `/v1/messages` endpoint.
Exports one function: `callClaude(system, user, apiKey)` → `Promise<string>`.

### Why
Isolating the HTTP call in its own module means every other module can be
tested without a network connection. The client is mocked in all tests
except the integration test in `word.generator.integration.test.ts`.

It also centralises the model name (`claude-sonnet-4-20250514`), token limit
(`4000`), and error handling in one place. When the model name changes,
one line changes.

### How
Uses the native `fetch` API. Passes `system` as the top-level `system`
parameter and `user` as `messages[0].content`. Extracts `data.content[0].text`
from the response. Throws `ApiError` (from `types.ts`) on non-2xx responses,
including the status code and body in the error for debugging.

Falls back to `process.env.ANTHROPIC_API_KEY` when no key is passed.

### Where
```
packages/word-generator/src/api/claude.client.ts
packages/word-generator/src/api/claude.client.test.ts

## Step 3-6 — `word.generator` (orchestrator)
⬜ **Pending**

### What
The orchestrator. Wires all five modules together into a single callable
function: `wordGenerator.generate(opts)` → `Promise<GeneratorResult>`.

### Why
Each module does one thing. The orchestrator decides *when* and *how many
times* to call them. It owns the retry logic: if `parseResponse` yields fewer
than `MIN_YIELD_FRACTION × count` words, it makes another API call and
merges the additional words into the running total. It stops when the target
count is reached or `maxRetries` is exhausted.

### How
```
buildPrompt(opts)
  → callClaude(system, user, apiKey)
  → parseResponse(raw, opts.count)
  → if yield < MIN_YIELD_FRACTION × count AND retries remain: retry
  → deduplicate(allNewWords, existingWords)
  → return { words: merged, duplicatesRemoved, apiCallCount }
```

The `word.generator` is the only module tested with a mocked `callClaude`.
The integration test (`word.generator.integration.test.ts`) makes a real API
call and is gated behind `SKIP_API_TESTS=true` in CI.

```
packages/word-generator/src/generator/word.generator.ts
packages/word-generator/src/generator/word.generator.test.ts
packages/word-generator/src/generator/word.generator.integration.test.ts
```

### Why

and writes the result via `csv.writer`.

Eventually `generate-book` will call this automatically when a word list is

### How
Flags: `--theme` (required), `--output` (required), `--existing` (optional),
`--count` (default 150), `--seeds` (optional), `--api-key` (env fallback),
`--dry-run` (print words, no write).

Flow:
1. Load existing words from `--existing` (empty array if not provided)
2. Call `wordGenerator.generate({ theme, seeds, count, existing })`
3. If `--dry-run`: print table to stdout, exit
4. Call `writeWordsCsv(result.words, outputPath)`
5. Print summary: N words written, N duplicates removed, N API calls made

## Step 3-6a — Word Length Analysis (woven into 3-4, 3-1, 3-6)
✅ **Complete — 182/182 tests (+28 new)**

### What
A `analyzeWordList(words)` function in `csv.writer.ts` that examines an
existing word list, classifies each word into a length bucket (short 3–5,
medium 6–9, long 10–15), computes how far the distribution is from the ideal
(35% / 45% / 20%), and returns recommended target fractions for the new batch.

The analysis summary is injected into the user prompt as a `WORD LENGTH
GUIDANCE` section, telling Claude specifically what mix to generate rather
than always using a static 25/50/25 split.

### Why
Short words (3–5 letters) are the most valuable for grid density — they slot
into narrow gaps between longer words and enable far more intersections. But
they're also the least interesting to solve. Long words (10+ letters) are
memorable and satisfying but create sparse grids when they dominate.

Without analysis, the generator always requests the same mix regardless of
what's already in the list. If an existing CSV has 40 long words and 5 short
ones, generating another static-mix batch makes the imbalance worse. With
analysis, the new batch is explicitly weighted toward short words to compensate.

### How
Three buckets:
- **Short** (3–5 letters): bridge words, high intersection value
- **Medium** (6–9 letters): core vocabulary, most theme-relevant
- **Long** (10–15 letters): anchor words, memorable answers

`computeTargets()` calculates how far each bucket is from the ideal
distribution, then amplifies the deficit by 1.5× and clamps to [0.05, 0.80]
so no bucket is ever fully excluded. The result is normalised to sum to 1.0.

The analysis summary includes a plain-English priority note when the
distribution is skewed (e.g. "short words are underrepresented — heavily
prioritise 3–5 letter words in this batch").

### Where
```
packages/word-generator/src/types.ts       — WordListAnalysis, LengthBucket types
packages/word-generator/src/csv/csv.writer.ts  — analyzeWordList(), toBucket()
packages/word-generator/src/prompt/prompt.builder.ts — accepts analysis param
packages/word-generator/src/generator/word.generator.ts — runs analysis on existing
```
